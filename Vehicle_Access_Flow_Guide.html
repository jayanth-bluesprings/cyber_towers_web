System Overview

How all the pieces fit together — hardware, software, and workflow engine.

What Happens When a Vehicle Scans?

Every vehicle carries an RFID card. When it approaches the gate, the driver holds the card to the scanner. The TimeWatch RFID reader sends a scan event to the backend server, which then triggers a Temporal workflow to decide what happens next.

🔧 Hardware Components
  • RFID Card Reader — reads the card number (CardID) when a vehicle approaches
  • LED Display Panel — shows ALLOW / DENY message to security guard and driver
  • TimeWatch Server — records all scans into the SQL database (CardRecord table)
  • Security Desk PC — where the guard monitors the dashboard and takes actions
💻 Software Components
  • Backend — Node.js/Express on port 5001. Receives scan events, triggers workflows
  • Frontend Dashboard — React app on port 3000. Live view + Reports + Config
  • Temporal Server — Workflow engine on port 7233. Makes all decisions durably
  • MSSQL Database — TimeWatch DB. Stores CardRecord, Personnel, AuditLog tables

What is Temporal?

⚡
Temporal = Durable, Reliable Decision Engine

Temporal is a workflow engine that runs code in a crash-proof way. If the server restarts mid-workflow (e.g., while waiting 10 minutes for a security decision), Temporal automatically resumes exactly where it left off. Each vehicle entry creates its own workflow instance that runs independently until the vehicle exits.

Unauthorized Vehicle

A vehicle scans whose RFID card is either unknown to the system or has no company code (PCode is empty or '-'). Security must decide within 10 minutes.

🚨
Unauthorized — Security Decision Required
Unknown card / PCode empty · Security has 10 minutes to decide
1
WF1 detects empty PCode → triggers WF3
After looking up the card, WF1 finds that PCode is empty or '-'. This means the person is not registered with any company in the system. WF1 calls executeChild('wf3UnauthorizedApproval', ...). WF1 pauses and waits for WF3 to finish.
WF3 startsexecuteChild (WF1 waits)
2
WF3: LED shows "Unauthorized" + security alerted
WF3 immediately: (a) displays UNAUTHORIZED — Contacting security. Please wait. on the LED; (b) broadcasts the scan to the live dashboard so the security guard sees it; (c) sends an alert email to the security desk with the vehicle details.
displayOnLED()broadcastDeniedScan()sendUnauthorizedAlert()
3
WF3: Audit log written + 10-minute timer starts
A ENTRY_DENIED_UNAUTHORIZED audit log entry is written. WF3 then enters a wf.condition(() => decision !== null, '10 minutes') wait. The workflow is dormant — waiting for a security decision signal from the dashboard.
ENTRY_DENIED_UNAUTHORIZED10 min timerdormant

Three Possible Outcomes from WF3

✅
Outcome A: Security APPROVES the vehicle
Guard clicks "Allow" on dashboard → sends securityDecisionSignal

The security guard reviews the vehicle, verifies the visitor, and clicks Allow on the dashboard. They fill in the vehicle number and optionally a visitor company name and reason. The dashboard posts to POST /api/security-decision, which signals Temporal WF3.

A1
WF3 receives securityDecisionSignal with action: 'approve'
LED shows ✓ ALLOWED — Welcome. Approved by security. An approval confirmation email is sent. Audit log: UNAUTHORIZED_APPROVED_BY_SECURITY. WF3 returns { approved: true } to WF1.
A2
WF1 resumes — no quota change for unauthorized vehicles
WF1 checks the returned value: wf3Result.approved === true. WF1 logs UNAUTHORIZED_ENTRY_STARTED, starts WF2 (overstay monitor), and enters dormant state waiting for the exit signal. Note: no slot count is changed — unauthorized vehicles don't occupy company quota.
❌
Outcome B: Security DENIES the vehicle
Guard clicks "Deny" on dashboard → sends securityDecisionSignal

The security guard decides the vehicle should not be admitted. Clicks Deny on the dashboard with an optional reason.

B1
WF3 receives action: 'deny'
LED shows ✗ DENIED — Access refused by security. A DENIED event is broadcast to the dashboard (vehicle shows as "Access Denied" in Reports). Audit log: UNAUTHORIZED_DENIED_BY_SECURITY. WF3 returns { approved: false }.
B2
WF1 receives result and ends
WF1 checks wf3Result.approved === false and immediately returns. No WF2, no slot change, no exit tracking. The workflow instance closes completely.
⏱️
Outcome C: No response in 10 minutes (Timeout)
Security did not act within the 10-minute window

The wf.condition() timer expires. WF3 automatically proceeds with denial — no human action needed.

⚠️
Auto-denial after 10 minutes

LED shows ✗ DENIED — No security response. Access not granted. A DENIED event is broadcast. Audit log: UNAUTHORIZED_TIMEOUT. WF3 returns { approved: false }. WF1 ends. The vehicle must leave.

Vehicle Exit

When a vehicle leaves Cyber Towers, their RFID card produces a PortNum=2 scan. This wakes up the dormant WF1 workflow and triggers the full exit sequence.

↩️

Exit scan received — backend sends exitSignal to WF1
TimeWatch records a PortNum=2 CardRecord. The backend identifies the matching active WF1 instance by cardId and sends the exitSignal via the Temporal client. WF1's dormant wf.condition() wakes up.

WF1 signals WF2 (the overstay monitor) to cancel. WF2's 24-hour timer is cancelled, and WF2 ends without sending any alert email. This prevents false overstay alerts for vehicles that exited normally.

WF1 returns. The workflow instance is marked as Completed in Temporal. All associated child workflows (WF2, WF7) have ended. The complete vehicle visit — from entry scan to exit scan — is durably recorded in the audit log.
WF1 completedAll workflows ended
🕒
What happens if WF2's 24-hour timer fires before the exit?

If the vehicle is genuinely still inside after 24 hours, WF2 sends an overstay alert email to the company admin and security. WF2 then continues with escalation alerts at 32h and 40h intervals. When the vehicle eventually exits and WF1 sends cancelOverstaySignal, WF2 stops all further alerts.

executeChild vs startChild — Key Difference

executeChild — WF1 WAITS

Used for WF3 and WF9. WF1 stops and waits for the child to complete and return a result. WF1 needs the decision before it can continue.

  • WF1 → executeChild(WF3) → WF1 pauses
  • WF3 finishes → returns { approved: boolean }
  • WF1 resumes with the result
startChild — WF1 CONTINUES

Used for WF2 and WF7. WF1 launches these in the background and does not wait. Both run in parallel with WF1.

  • WF1 → startChild(WF2) → WF1 continues immediately
  • WF2 runs independently for 24h
  • WF1 doesn't wait — goes to dormant state

Signal Communication Map

Temporal Signals are messages sent into running workflows from the outside. This is how the dashboard, security guards, and workflows communicate with each other.

📡
What is a Temporal Signal?

Imagine a workflow is sleeping, waiting for something to happen. A Signal is like pressing a button that wakes it up and tells it what happened. Signals are durable — if the server crashes, the signal is not lost. When the server restarts, the workflow receives the signal and continues.

All Signals in the System

Signal Name Sent By Received By Payload What It Does
exitSignal Backend (PortNum=2 scan) WF1 { timestamp, gate } Wakes up dormant WF1. Triggers exit processing.
securityDecisionSignal Dashboard Allow/Deny button → POST /api/security-decision WF3 { action, officerId, vehicleNumber?, reason? } Delivers the security officer's approve or deny decision to WF3.
overrideRequestSignal Dashboard "Request Override" button WF9 None Notifies WF9 that security wants an admin override. Triggers admin email.
adminDecisionSignal Company Admin email link click WF9 { action, adminId, reason? } Delivers the admin's approve or deny decision to WF9.
cancelOverstaySignal WF1 (on vehicle exit) WF2 None Cancels the 24-hour overstay timer. Prevents false alert emails.
vehicleExitedSignal WF1 (on vehicle exit) WF7 { timestamp, gate } Tells WF7 the vehicle has left. WF7 broadcasts updated slot count and ends.

Data Flow — Dashboard & Reports

The frontend dashboard has two data sources that are merged together to provide a complete picture of vehicle activity.

Two Data Sources

📀 Source 1: CardRecord Database (SQL)
  • What it contains: Real RFID card scans from the TimeWatch system
  • When it's updated: Immediately when any RFID reader records a scan
  • Used by: Live Entry/Exit page, Reports page, Stats APIs
  • Table: CardRecord in MSSQL TimeWatch DB
  • Limitation: Only has real hardware scans — no simulator events
⚡ Source 2: temporalEvents (In-Memory)
  • What it contains: Events broadcast by Temporal workflows via WebSocket
  • When it's updated: Every time a workflow broadcasts ENTRY, EXIT, or DENIED
  • Used by: Reports page (prepended), Stats APIs (vehicle count)
  • File: backend/temporalEvents.js
  • Limitation: In-memory only — cleared on server restart

Reports Page — Session Building Logic

🔧
How temporalEvents.buildSessions() works

The in-memory event store pairs ENTRY events with EXIT and DENIED events to build session records that match the shape of CardRecord rows. This allows the Reports page to show Temporal simulator traffic with proper "Exited", "Still Inside", and "Access Denied" statuses.

Event SequenceResulting Status
ENTRY → EXITExited — Normal completed visit
ENTRY (no EXIT yet)Still Inside — Vehicle currently in premises
ENTRY → DENIEDAccess Denied — Entry was denied after being held
Standalone DENIEDAccess Denied — Denied without prior ENTRY record

Appendix

Glossary & Key Terms

Quick reference for all technical terms used in this document.

TermMeaning
TemporalThe workflow engine powering all vehicle access decisions. Ensures workflows survive server restarts, crashes, and network failures.
Workflow InstanceOne running copy of a workflow. One WF1 instance is created for each vehicle visit. Multiple instances can run simultaneously.
SignalA message sent into a running workflow to wake it up and provide data (e.g., security decision, exit notification).
ActivityA single unit of work inside a workflow — e.g., looking up a card in the database, sending an email, updating the LED.
CardIDThe RFID card number embedded in the physical card carried by employees/visitors.
PCodeCompany code. Identifies which company the cardholder belongs to. Empty/'-' means unauthorized.
PortNum1 = Entry scan, 2 = Exit scan. Determined by which reader captured the scan.
LED PanelThe display board at each gate. Shows ALLOWED or DENIED messages. There is no automated barrier at Cyber Towers.
temporalEventsIn-memory event store in the backend. Stores Temporal workflow events so they appear in the Reports and Stats pages.
executeChildStarts a child workflow and WAITS for it to finish. WF1 uses this for WF3 and WF9 so it can act on their decision.
startChildStarts a child workflow and DOES NOT wait. WF1 uses this for WF2 and WF7 which run in the background.
wf.condition()A durable wait inside a workflow. The workflow sleeps until a condition becomes true or a timeout occurs.
QuotaThe number of parking slots allocated to a company. e.g., Microsoft India has 22 total slots.
OverrideAllowing a vehicle to enter even though the company's quota is full. Requires admin approval.
Audit LogA permanent database record of every significant event: entry, exit, approval, denial, report sent, etc.
WebSocketA real-time connection between backend and frontend. Used to push live updates to the dashboard without page refresh.
Task QueueThe Temporal queue name: cyber-towers-task-queue. All workflows and activities use this queue.
