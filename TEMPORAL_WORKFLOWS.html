1. What is Temporal — Key Concepts Reference

ConceptWhat It Means (Plain English)Used In This Project For
WorkflowA function that runs as a long-running business process. It can sleep for hours or days and will resume exactly where it left off — even after a server crash.Tracking a vehicle from entry to exit, running scheduled reports
ActivityA single unit of work inside a workflow — like querying the DB, sending an email, or writing a record. Activities are retried automatically if they fail.Sending alert emails, querying CardRecord table, updating parking
SignalA message sent INTO a running workflow from outside. The workflow is waiting for something to happen in the real world.Vehicle exit scan arriving, security officer approving an entry
QueryReading the current state of a running workflow without changing anything.Dashboard asking "is this vehicle still inside?" live
Timer (sleep)await sleep('24 hours') — Temporal stores this timer. Your server can restart, and the timer will fire at the right time.24-hour overstay detection per vehicle
ScheduleRun a workflow on a cron schedule. If the server was down when it was supposed to run, Temporal runs it when the server comes back.Daily report at 11:59 PM, weekly report on Fridays
Child WorkflowA workflow started by another workflow. Can be waited for or detached (runs independently).Overstay Alert started by Vehicle Session workflow
WorkerYour Node.js process that runs workflow and activity code. Connects to the Temporal server.The backend server.js will also start a Temporal Worker

2. Why This Project Needs Temporal

The vehicle access dashboard manages time-sensitive, stateful business processes. A vehicle enters and must be tracked for potentially 24+ hours. An unauthorized vehicle needs a security officer's decision within 30 minutes. Daily report emails must be sent even if the server went down at 11:59 PM and came back at 12:03 AM. These are all durable workflows — they must survive crashes, remember state, and react to real-world events.

Currently, all of this is handled by node-cron (which forgets on restart), in-memory JavaScript objects (lost on crash), and browser localStorage (not reliable for business workflows). Temporal is designed exactly for this problem.

3. Current Problems in the Codebase (Precise)

Problem 1 — backend/services/cronJobs.js

// Line 7 — In-memory warning tracker (wiped every server restart)
const warned24hVehicles = {};

// Line 238 — If server is down at 11:59 PM, this email is NEVER sent
// node-cron has no catch-up logic for missed schedules
cron.schedule('59 23 * * *', () => { sendDailySummary(); });

What we lose: After a server restart, all vehicles previously warned about overstay are warned again (duplicate emails). If the server is down at 11:59 PM, the daily summary is permanently missed.

Problem 2 — frontend/src/utils/localAccessApprovalsStorage.js

The unauthorized vehicle approval system lives in the browser's localStorage. If security opens the dashboard in a different browser tab, they don't see approvals from the first tab. There is no timeout — unauthorized vehicles stay "pending" forever. There is no server-side record of who approved what and when.

Problem 3 — No Gate Health Monitoring

The getEventCounts function in statsController.js does check RFID vs traffic light mismatch — but only when a user manually clicks the Health Check button on the dashboard. There is no automated alerting if Gate 1's RFID reader stops working at 2 AM.

Problem 4 — Fragile Personnel Cache

In personnelCache.js, the cache is refreshed synchronously inside the WebSocket poll loop (line 55 of websocket.js: const personnelMap = await getPersonnelMap()). If the DB is slow, this blocks real-time scan broadcasting. On server restart, the cache is cold.

Workflow 1
Vehicle Session Lifecycle
One workflow per vehicle entry — tracks entry to exit with durable state
Type: Event-driven, per-vehicle
Duration: Minutes to 72 hours
Trigger: PortNum=1 scan detected
Priority: 3 of 8

Purpose

This is the core workflow of the entire system. One instance runs for every vehicle that enters the premises. It holds live state for a vehicle session — entry time, gate, vehicle type — and waits for either an exit scan signal or a timeout. All other vehicle-related workflows (overstay alert, parking management) are started as children of this workflow.

What Problem It Solves

Current Code

Session reconstruction happens at query time via the SQL CTE buildSessionCTE in reportcontroller.js lines 7–60. The system has no live, running state per vehicle. Every time the occupancy page is loaded, it re-runs the entire CTE. There is no way to ask "is this specific vehicle inside right now?" without a DB query.

Trigger

The WebSocket polling loop in websocket.js detects a new RFID entry scan (PortNum=1) and starts a new Temporal Workflow.

Workflow ID: vehicle-session-{CardData}-{entryTimestamp}

Signals (Inputs While Running)

Signal NameSent ByPayloadEffect
vehicle-exitedWebSocket polling (PortNum=2 scan)exitTime, exitGate, exitCardRecordIdCompletes session, cancels overstay child
manually-closedAdmin from dashboardreason, adminNameForce-closes session if RFID exit failed

Queries (Read State Without Changing It)

Query NameReturnsUsed By
getSessionStatusstatus, entryTime, vehicleType, hoursInsideDashboard occupancy API, health check
isInsidePremisesbooleanOverstay workflow checking if vehicle still inside

Workflow Steps

1
ACTIVITY recordEntryToAuditLog(entryData)

Write entry event to audit log. Retry: 5 times with 10s exponential backoff.

2
ACTIVITY checkParkingSlotAssignment(cardData)

Query parking allocations for this card. Returns: { hasSlot: boolean, slotLabel: string | null }

3
If no parking slot: CHILD WORKFLOW ParkingSlotManagementWorkflow

Start Workflow 7 as a detached child (runs independently). Do not wait for it.

4
CHILD WORKFLOW Start OverstayAlertWorkflow (Workflow 2)

Pass: cardData, entryTime, vehicleType, pCode. This child runs independently and handles the 24-hour timer.

5
WAIT Signal('vehicle-exited') OR Signal('manually-closed')

The workflow sleeps here — could be minutes, hours, or days. Temporal's durable timer keeps this alive across server restarts.

6
On 'vehicle-exited' signal:

Cancel OverstayAlertWorkflow child. Record exit to audit log. Release parking slot. Compute session duration. Workflow ends successfully.

7
MAX TIMEOUT (72 hours):

If neither signal received in 72 hours, send final critical alert and terminate workflow.

Workflow 2
Overstay Alert & Escalation
Per-vehicle durable 24-hour timer — survives server crashes — replaces cronJobs.js
Type: Child of Workflow 1
Duration: 24–72 hours
Trigger: Started by Workflow 1 on entry
Priority: 2 of 8 (high)

Purpose

One instance of this workflow runs for every vehicle that enters. It waits exactly 24 hours from entry time using Temporal's durable timer. If the vehicle exits before 24 hours, the parent workflow cancels this child cleanly. If the vehicle is still inside after 24 hours, it sends an alert and continues escalating every 12 hours.

The Key Problem It Fixes

❌ Current Code (cronJobs.js)
  • warned24hVehicles is an in-memory JS object — wiped on every server restart
  • Cron runs every 30 minutes checking ALL vehicles — inefficient SQL query every 30 min
  • Server crash at 3 AM → all vehicles warned again on restart (duplicate emails)
  • No escalation after first 24h alert
✅ With Temporal
  • Per-vehicle timer — each vehicle has its own independent 24h countdown
  • Timer stored in Temporal's event history — survives any crash
  • No duplicate alerts on restart — state is durable
  • Built-in escalation: 24h → 36h → 48h → 72h

Workflow Steps

1
TIMER sleep('24 hours') from entry time

If vehicle exits before this fires, Workflow 1 cancels this child workflow. Timer is discarded. If server restarts during this 24h wait, Temporal resumes the timer where it left off.

2
Timer fires — vehicle still inside after 24 hours:

ACTIVITY fetchVehicleDetails(cardData) — get latest info from Personnel cache.
ACTIVITY sendOverstayAlertEmail({ cardData, vehicleType, pCode, entryTime, hoursInside: 24 }) — Retry 5 times, 30s backoff.

3
LOOP Every 12 hours — check if still inside:

ACTIVITY checkVehicleStillInside(cardData) — queries Workflow 1's isInsidePremises query.
If still inside: send escalation email with increasing urgency. If exited: workflow ends cleanly.

4
At 72 hours — final critical alert:

ACTIVITY sendCriticalEscalationEmail() — to Admin + Facility Manager + Security Head.
Workflow terminates after this.

Workflow 3
Unauthorized Vehicle Approval
Server-side approval process — replaces localStorage — with timeout & notifications
Type: Event-driven, per unauthorized entry
Duration: Up to 2 hours
Trigger: PortNum=1 scan with empty PCode
Priority: 4 of 8

Purpose

When an unregistered vehicle (empty PCode) enters the gate, this workflow starts. It notifies the security officer on duty, then waits for a human decision — approve or deny. The entire approval process is server-side, durable, and has a timeout. No more browser localStorage approvals that disappear when the tab is closed.

What Problem It Fixes

Current Code Location

LiveEntryExitPage.jsx lines 276–310 and LiveTable.jsx lines 261–295 — both store approvals in vehicleAccess.localApprovals.v1 localStorage key. If security opens a different browser, they see different approval data. There is no 30-minute timeout. No server notification sent.

Signals (Human Input Into the Workflow)

Signal NamePayloadSent ByEffect
approval-grantedvehicleNo, remark, approvedBy, approvedAtSecurity officer via dashboardGrants access, stores in audit log, broadcasts to all dashboard clients
approval-deniedreason, deniedBySecurity officerMarks as denied, triggers security alert

New API Endpoints This Requires

POST /api/approvals/grant
  Body: { workflowId, vehicleNo, remark, approvedBy }
  → Sends 'approval-granted' signal to the running workflow

POST /api/approvals/deny
  Body: { workflowId, reason, deniedBy }
  → Sends 'approval-denied' signal

GET /api/approvals/status/:cardData
  → Queries the workflow: returns { status: 'pending'/'approved'/'denied'/'timed-out' }

Workflow 4
Daily Summary Report
Scheduled 11:59 PM every night — catches up if server was down
Type: Scheduled (Temporal Schedule)
Schedule: 59 23 * * * (11:59 PM daily)
Duration: ~5 minutes
Priority: 1 of 8 (easiest & most impactful)

Purpose

Generate and send the nightly vehicle access summary email. Same business logic as today's sendDailySummary() — but with guaranteed delivery even if the server was down at 11:59 PM, email retry logic, and additional metrics (unauthorized entries, vehicle type breakdown).

Workflow Steps

ACTIVITY fetchDayEntryExitStats(reportDate)

Query CardRecord for today's totals. Retry: 5 times, 30s backoff. Timeout: 2 minutes per attempt.

2
ACTIVITY fetchCurrentlyInsideCount()

Count active VehicleSession workflows (vehicles still inside). Retry: 3 times.

3
ACTIVITY fetchUnauthorizedEntryCount(reportDate)

NEW metric — how many unauthorized scans occurred today. Not in current code.

Build HTML email body with all collected statistics.

5

Workflow 6
Gate Health Monitor
Singleton — runs forever — alerts when RFID reader goes silent
Type: Singleton, runs continuously
Duration: Forever (until stopped)
Trigger: Started once when server boots
Priority: 5 of 8

Purpose

Every 5 minutes during business hours (8 AM – 8 PM), check if each gate's RFID reader has sent at least one scan in the last 30 minutes. If Gate 1 or Gate 2 is silent during business hours, alert the facility manager. This is entirely new functionality — no equivalent exists in the current codebase.

Workflow 8
Vehicle Registry Sync
Every 55 seconds — proactive cache warm — decouples DB from live scan path
Type: Scheduled (every 55 seconds)
Duration: ~10 seconds
Trigger: Temporal Schedule
Priority: 8 of 8 (lowest urgency)

Purpose

The Personnel cache in personnelCache.js is currently refreshed synchronously inside the WebSocket poll loop. This means a slow DB query can delay real-time scan broadcasting. This workflow moves cache refresh to a background scheduled process, so the live scan path never has to wait for a DB query.

What This Fixes

In websocket.js line 55:

// CURRENT — DB query happens synchronously inside the 3-second poll loop
// If DB is slow, this delays broadcasting new scans to the dashboard
const personnelMap = await getPersonnelMap(); // ← problem

// WITH TEMPORAL — personnelMap is always pre-cached by a background workflow
// The poll loop just reads from cache, never waits for DB
const personnelMap = getCachedPersonnelMap(); // instant

New Dashboard Metric This Enables

The Health Check modal in Dashboard.jsx currently only shows "Database: Reachable". With this workflow:
